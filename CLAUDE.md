# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

BhoomiSetu is a direct land marketplace prototype for Mysuru: sellers list land, buyers swipe to shortlist, and every asking price is checked against nearby listings before it's shown. No agents in the middle.

It is backed by a real Supabase (Postgres + file storage) project — not mocked data. Buyers and sellers log in with full name + mobile number + password (see "Auth" below for how that's actually implemented under the hood). Phone calling between matched parties is a real `tel:` link, not masked/anonymized. These are known, intentional gaps, not bugs to silently "fix" — see "Known gaps" below before changing auth-adjacent or calling-adjacent code.

## Commands

```bash
npm install       # install deps
npm run dev       # start Vite dev server, http://localhost:5173
npm run build     # production build
npm run preview   # preview the production build
```

There is no lint script and no test suite configured in this repo.

### Database setup (required before the app will run)

The app hard-fails to a "Database not connected" screen (see `isSupabaseConfigured` in `src/lib/supabaseClient.js`) unless `.env` has `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` set from a real Supabase project. Schema changes live in `sql/schema.sql` and must be applied by hand in the Supabase SQL Editor — there is no migration tool; `sql/schema.sql` is the source of truth for a **fresh** project, but it has already been run once against the live project this repo points to, so incremental changes need a new numbered migration file (`sql/migrations/NNN_verb_description.sql` — zero-padded number, snake_case, starting with a verb, e.g. `006_require_encumbrance_certificate.sql`) with `ALTER`-based statements, applied by hand, in addition to updating `schema.sql` itself to keep it accurate for a hypothetical fresh install. The project's Supabase dashboard also needs **Authentication → Providers → Email → "Confirm email" turned off** — required for signup to complete (see "Auth" below). The `account-recovery` Edge Function (forgot-password, see "Auth") must be deployed separately via the Supabase CLI (`supabase functions deploy account-recovery`) but needs no secret — Supabase injects `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` into every function automatically. Admins (who see the Review tab) are added by hand: `insert into admins (user_id) select id from auth.users where email = '91XXXXXXXXXX@bhoomisetu.local';` — there is deliberately no in-app way to become an admin.

### Auth

Login is phone+password, but there is **no Supabase phone-auth and no SMS provider** — Supabase's hosted platform requires a paid SMS provider before its native `phone` field can be used at all, even without OTP, which this project doesn't have. Instead, `src/lib/auth.js` uses Supabase's built-in **email+password** auth with a synthetic, never-emailed address derived from the phone number (`91XXXXXXXXXX@bhoomisetu.local`). The UI never shows this — components only ever pass/receive a phone number; `normalizePhone()`/`signUp()`/`signIn()`/`currentUser()` in `auth.js` are the only places that know about the synthetic-email trick. Don't "simplify" this back to a real phone-auth call without first setting up an actual SMS provider — it will break signup entirely on the hosted project.

**Forgot password = one-time recovery code**, because nothing can ever receive a reset link at the synthetic address and there's no SMS. `supabase/functions/account-recovery` has two actions: `issue` (logged-in user, JWT-verified; replaces any older code) and `reset` (phone + code + new password; changes the password via the admin API and returns a *new* code, so each code works once). Only a SHA-256 hash lives in `recovery_codes` (RLS on, no policies — service role only). A code is issued right after signup and can be regenerated from `ProfileView`; `App.jsx` owns the `RecoveryCodeModal` because `AuthView` unmounts the instant a session lands. Supabase's `resetPasswordForEmail` is useless here — don't reach for it. `normalizePhone`/`validatePassword` are mirrored inside the function; keep both copies in sync.

## Architecture

**Data flow is intentionally single-directional and centralized:**

- `src/App.jsx` is the only stateful container. It tracks the Supabase Auth session (`getSession`/`onAuthStateChange` from `lib/auth.js`) alongside `listings`, plus — once a user is known — `swipes`, `contacts` (`{listingId: phone}`, whatever RLS lets this user see), `interest` (`{listingId: rightSwipeCount}` for their own listings) and `isAdmin`, and passes everything down as props. Only the *first* load shows the full-screen "Loading…"; later `refresh()` calls update data in place so the current view keeps its local state (e.g. SellView's "published" screen). It switches between views (`home` / `sell` / `buy` / `matches` / `profile` / `review` (admins only) / the implicit auth screen) via a simple `view` string in state — there is no router. Everything except `home` is gated: if `view` is one of those and there's no logged-in user, `AuthView` renders instead of the requested view, and once login succeeds the auth-state subscription alone is what causes the real view to render (no redirect/callback plumbing).
- `src/lib/storage.js` is the **only** module allowed to talk to Supabase's database/storage. All reads/writes (listings, images, documents, swipes) go through its exported functions. When adding a new piece of persisted data, add the query function here rather than calling `supabase` directly from a component. `src/lib/auth.js` is the equivalent single entry point for Supabase **Auth** calls (signup/login/logout/session) — keep that separation rather than calling `supabase.auth.*` from components.
- `src/lib/supabaseClient.js` creates the single Supabase client and exposes `isSupabaseConfigured`, which gates whether `App.jsx` renders the app or the "not connected" screen.
- `src/lib/pricing.js` holds the price-fairness logic (`priceCheck`): it compares a listing's ₹/sqft against the average of other listings in the *same locality* and buckets it into `high` / `low` / `fair` / `insufficient`. This is a rough local-average comparison, explicitly not a certified valuation — both `SellView` (live preview while filling the form) and `BuyView` (badge on the swipe card) call it against the full in-memory `listings` array, so it recomputes client-side rather than being a stored/server value.
- Buyer/seller identity is a real Supabase Auth user id (`user.id` from `currentUser(session)` in `auth.js`) — the `listings.seller_id` and `swipes.buyer_id` columns key off of it, and RLS enforces `auth.uid() = seller_id` / `auth.uid() = buyer_id` on writes.
- `src/lib/image.js` generates a deterministic placeholder SVG (as a data URI) for listings with no uploaded photos, keyed by listing id/location — used so demo/seed listings don't depend on external image URLs.

**Views** (`src/components/*View.jsx`) are presentation + local UI state only (form fields, drag position, etc.); they call into `storage.js`/`auth.js` for persistence and receive `listings`/`swipes`/`user` from `App.jsx` as props rather than fetching their own data. `AuthView` handles login, signup and forgot-password (a `mode` toggle, not three files). `ListingDetail` is a shared full-screen sheet (all photos, description, price breakdown) opened from Browse, Matches, the seller dashboard and Review — callers pass their own action buttons as `children`. `ProfileView` edits the account name (and re-syncs the denormalized `listings.seller_name`), changes password (re-checks the current one first), and regenerates the recovery code. `ReviewView` is the admin ownership-review queue. `SellView` is a dashboard, not just a form: it lists the logged-in seller's own listings (filtered client-side from the full public `listings` array by `l.sellerId === user.id`) with Edit/Delete, and reveals the create/edit form (one shared form, an `editingListing` flag distinguishes the two) on demand — sources the seller's name/phone from `user` rather than a form field, and uploads images/documents as part of `createListing`/the edit-save flow. `BuyView` implements the swipe-card drag gesture, computes the price badge per-card, and has client-side filters (locality / type / price band / verified-only); rejected listings never reach it. `MatchesView` reads `swipes.liked` and shows a contact only where `contacts` has one — a missing entry means "not unlocked yet", not an error. The seller dashboard shows interest as a **count only** — buyer identities are never exposed to sellers.

**Owner verification (anti-agent) — hybrid by design.** A seller declares `document_owner_name` (as printed on the EC, plus the RTC for agri). An admin compares it against the document and the account name on the Review page (`src/lib/nameMatch.js` is an advisory hint only, never an auto-decision — no AI/OCR on documents, for privacy). Pending listings still appear in Browse (with a badge) and can be shortlisted, but the seller's phone only unlocks for buyers once the listing is `verified`; `rejected` listings are hidden from Browse and the seller sees the admin's reason. The **database** enforces this, not the UI: the phone lives in `listing_contacts` (RLS: own listing / admin / right-swiped + verified), and the `guard_listing_verification` trigger stops non-admins from setting any status except `pending`, and resets to `pending` when locality/type/area/dimensions/owner name change or a new EC/Khata/RTC is uploaded (price/title/description edits keep verification). Don't move the phone back onto `listings` — that table is publicly readable.

**No photo-content check right now.** An earlier Gemini-based "does this photo look like land" Edge Function (`classify-photo`) was removed on 2026-09-26 — the plan is to replace it later with a proper ML classifier (land / house / agri land / not suitable). Sellers' photos are currently uploaded without any content check.

## Database model (`sql/schema.sql`)

- `listings` — one row per land parcel (title, location, type, unit, area, `dimensions` (nullable raw "60x30" text, sqft-unit listings only — see `src/lib/dimensions.js`), price, advantages array, optional `description`, `seller_id` + denormalized seller name, `document_owner_name`, `verification_status` (`pending`/`verified`/`rejected`) + `verification_note` + `verified_at`). The seller's phone is **not** here — see `listing_contacts`. `seller_id` is nullable — pre-auth/seed rows have no owner, but every row the app inserts always sets it (RLS-enforced). Sellers can update/delete their own rows via `SellView`'s dashboard.
- `listing_images` — public bucket `land-images`; rows reference `listings.id` with an `is_primary` flag used for card ordering. Exactly one image per listing should be `is_primary` whenever any images exist — `ensurePrimaryImage()` in `storage.js` enforces this after any add/remove, since letting the add-path and remove-path each guess independently can leave two images flagged primary at once.
- `listing_documents` — private bucket `land-documents`. Four typed slots via `doc_type` (`check` constraint, no default — callers always specify one): `'ec'` (Encumbrance Certificate) is **required for every listing**; `'khata'` (E-Khata, optional for `site`/`commercial`) and `'rtc'` (RTC, required for `agri`) are the type-specific doc, mutually exclusive per listing — see `EC_DOC`/`PROPERTY_TYPES` in `src/data/propertyTypes.js`; `'tax_receipt'` is always optional. Deliberately **no personal-ID document type** — this is proof-of-property, never Aadhaar/PAN; don't add one without a real conversation about why. Only **admins** can read documents (select policy `is_admin()` on the table and on the `land-documents` bucket, used by `ReviewView` via short-lived signed URLs) — sellers can't read back even their own, and there must never be a public read policy. Because sellers can't select, replacing a document during edit (`replaceListingDocuments()`, plural — scoped per `doc_type`, so replacing an EC never touches the Khata/RTC row) can delete the old DB row (by `listing_id` + `doc_type`, no select needed) but can never learn the old file's `storage_path` to clean it up from the bucket — the old file is deliberately left orphaned in storage. Same for whole-listing delete: image storage files are cleaned up (their paths are known, via the public-read `listing_images`), document storage files are not. The mandatory-doc check only runs at **create** time (`SellView.handleSubmit`) — it can't be enforced on edit for the same no-select reason, so edit never forces re-upload.
- `swipes` — one row per (buyer_id, listing_id), unique constraint enforces upsert-on-swipe semantics; `direction` is `left`/`right`. Sellers read aggregate counts through the `my_listing_interest()` security-definer function, never the rows.
- `listing_contacts` — one row per listing holding `seller_phone`, split out of `listings` so it isn't public. Readable by the listing's seller, admins, and buyers who swiped right on a *verified* listing.
- `admins` — user ids allowed to review. Users can only read their own row; rows are inserted by hand in the SQL Editor. `is_admin()` (security definer) is what every admin policy calls.
- `recovery_codes` — hashed forgot-password codes, one per user; RLS on with no policies, so only the `account-recovery` Edge Function (service role) touches it.

**RLS is scoped to real auth on `listings`, `listing_images`, `listing_documents`, and `swipes`.** `listings` insert/update/delete require `auth.uid() = seller_id`. `listing_images`/`listing_documents` insert/delete are scoped via an `exists (select 1 from listings where ... seller_id = auth.uid())` subquery — i.e. you can only attach/remove images or documents on a listing you own. Admins additionally get update on any listing (to set verification) and read on documents. Reads on `listings`/`listing_images` stay public (Home's listing count and Browse itself aren't gated). The `land-images` storage bucket has a delete policy (bucket-level only, not ownership-scoped — the real check happens at the table level above); `land-documents` intentionally has no delete policy, consistent with the orphaned-document-file note above.

## Known gaps (don't silently "complete" these without being asked)

- Forgot-password only works via a saved recovery code — a user who lost both password and code can't get back in (no SMS/email exists).
- Mobile number can't be changed (it *is* the login).
- No masked/anonymized calling — `MatchesView` uses a plain `tel:` link, so the seller's real number is visible to the buyer (not proxied through a telephony provider).
- Only the "document owner name + admin review" anti-agent step is built. Not built (discussed 2026-09-26, deferred): per-account caps on pending listings, a resale cooling-period flag, Aadhaar eKYC.
- Replacing/deleting a document orphans the old file in the `land-documents` storage bucket (see above) — not cleaned up, by design given the no-select-policy constraint.
- No payments — including the discussed token-advance/escrow flow (needs a real escrow partner, e.g. Razorpay Escrow; can't legally hold funds in a normal account).
